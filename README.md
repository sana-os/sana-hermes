# sana-hermes

SANA OS（https://github.com/sana-os/sana-os ）を Hermes Agent のプロファイルで動かすためのファイル一式です。
SANA OS のリポジトリを正本とし、`build.py` がそこから Hermes 用の `SOUL.md` とスキルを生成します。`dist/` 以下はすべて生成物なので、SANA OS が更新されたら作り直せます。

Powered by SANA OS — https://sana-os.org
（SANA OS License v1.0 に基づく派生物です。Core_Principle.md は無改変で含めています。）

- 生成元: `sana-os/sana-os` コミット `96f08c4f8465`（2026-04-05, "Full replace — SANA OS v1.0"）
- 動作確認に使った Hermes のソース: `NousResearch/hermes-agent` `b65e078`（2026-10-16）

## 中身

```
sana-hermes/
├─ build.py                 生成スクリプト（Python 3.9+、標準ライブラリのみ）
├─ sana-hermes.json         プロファイルとスキルの定義
├─ overlays/
│  ├─ Persona_Hub.custom.md     ハブ用ペルソナ（新規。Persona_Template の 2・3 章として書いたもの）
│  ├─ Persona_Review.custom.md  レビュー用ペルソナ（同上）
│  ├─ Persona_Friend.custom.md  フレンド用ペルソナ（同上）
│  ├─ skills/                   このパッケージで書いた手順（レビュー3つと物語の考察。SANA OS の一部ではない）
│  └─ hermes_runtime_notes.md   各 SOUL.md の末尾に付く Hermes 用の注記
├─ install.ps1              Windows 用インストーラ
└─ dist/
   ├─ mode-skills/          標準（フレームワークをスキルとして必要時に読む）
   └─ mode-inline/          比較用（GPTs と同じく全フレームワークを SOUL.md に展開）
      ├─ MANIFEST.json      生成元コミット、各ファイルのハッシュ、文字数、検査結果
      └─ profiles/<名前>/SOUL.md, skills/sana-os/<スキル>/SKILL.md
```

## 組み立て方と、その理由

**SOUL.md ＝ Core 3ファイル ＋ ペルソナ ＋ Hermes 注記**

GPTs で「全部を順に貼る」形を、Hermes の作りに合わせて次のように分けました。

| SANA OS | Hermes での置き場所 | 理由 |
|---|---|---|
| Core_Principle / Integrated_Knowledge / Communication_Layer | SOUL.md（常時） | 毎ターン働く OS の部分。Integrated_Knowledge はスキルを選ぶ索引も兼ねる |
| personas/Persona_*.md | SOUL.md の末尾（常時） | 「ペルソナは最後に読む」という元の順序を保つ |
| frameworks/*.md | スキル（必要時に読む） | 元の README でも「常時ではなく、該当する構造が見えたときに使うレンズ」とされている |
| Core_Specification.md | ハブのスキルのみ | 元の README で「AI に読ませる必要はない開発者向け資料」とされているため、実装を設計するハブにだけ渡す |

**SANA OS の本文は書き換えていません。** `build.py` は Core_Principle.md が SOUL.md の中にバイト単位で同一のまま入っていることを毎回検査し、違えば失敗します。各フレームワークのスキル本文も原文のままです。足したのは次の3つだけです。

1. **各スキルの冒頭の「Viewpoint (invariant)」**：そのレンズが何を見るものか、を一段落で。手順や例は研ぎ澄ましていくが、視点は変えない、という区別をスキルの中に書いておくためです。将来スキルを改良するとき、「研ぎ澄ましたのか、ずらしたのか」を判断する基準になります。
2. **SOUL.md 末尾の Hermes Runtime Notes**：使えるスキルの一覧と、「レンズを使うときは名前の記憶ではなく `skill_view` で中身を読んでから」「ツールの結果は、その時点の環境の Record」「利用者の言語で答える」の3点。
3. **ハブのペルソナ**（下記）

**ハブのペルソナ**は SANA OS に存在しないため、Persona_Template から作りました。0章（8つの不変条件）と1章（処理順序）はテンプレートの文面をそのまま使い、2・3章だけを書いています。中身は、これまで話してきた方針をそのまま規則にしたものです。どの項目にも理由を添えています。

- 設計は雛形まで。大きな構築はタスク実行者に、理由つきの設計書と「判断できないときは戻す」経路を付けて渡す
- 観察したこと・利用者が言ったこと・推論を分けて報告する
- 永続メモリには「決定／検討中／仮説」と日付を付ける
- 決定の理由・検討した選択肢・きっかけになった観察を残す
- 取り消せない操作（データ削除、公開リポジトリの main、スキーマ変更）は準備して止まり、承認を待つ
- 推論の途中で足りなかったデータや道具を、環境の要件として拾う

**レビューのペルソナ**も Persona_Template から作りました。0〜1章（不変条件と処理順序）はハブと共通で、2〜3章をレビュー用に書いています。

- **SANA の定義を「人格」ではなく「仕様」として持つ**：不変条件（敵対しない、観察が先、構造で見る、自律を尊重する）は、レビューの「やり方」として共有します。一方で、SANA の定義は「何をレビューするか」の仕様として持ちます。作者と不変条件は共有しても、作者の声や結論は共有しない、という位置づけです。レビュアーが作者の前提を借りると、作者自身も気づける誤りしか見つけられないからです。
- **正しさではなく、置き場所を見る**：見るのは「その記述は、足場が許す場所に置かれているか」です。Fact／Perception／Record、利用者の決定、推論、印のついた仮説のどれにあたるかを確かめます。印のついた大胆な仮説は誤りではありません。同じ文が「知られている」という形で出てきたら指摘します。
- **推測を罰しない**：「間違っているかもしれないから消して」とは言わず、「印をつける・足場を示す・置き場所を直す」ことだけを求めます。慎重さを褒めるレビューは、作者に推論を書かせなくなり、理由の蒸発を招くからです。
- **その時点で知り得たことで判断する**：後知恵で、外れた判断を「誤り」、当たった判断を「先見の明」と見ないためです。
- **書き換えない**：指摘し、問い、確かめ方を示すところまでにします。リポジトリやファイルには手を触れません。書き換えるレビュアーは二人目の作者になり、その書き換えは誰もレビューしないからです。
- **確かめられなかったことを書く**：書かれていない穴は「確認済み」に見えてしまうからです。
- **自分の推論にも印をつける**：`【レビュアーの見立て】` を使います。他者に課す規則を、自分にも適用するためです。

出力の形は「対象と基準 → 指摘（重要度順、最大7件。各項目に箇所・ずれの種類・見立てと確信度・確かめ方・作者への問い）→ 保たれている点 → 戻し先（作者／ハブ／利用者）」です。

観点ごとの手順は、スキルとして分けました。どれも SANA OS の一部ではなく、このパッケージで書いたものです。

| スキル | 対象 | 主に見るもの |
|---|---|---|
| `sana-review-history` | History SANA の観察・分類・仮説 | 観察の誤り、観察への解釈の混入、Fact の位置に置かれた推論、固有名と年代、F/P/R のずれ、模写を原本として扱っていないか、印のない仮説 |
| `sana-review-design` | ハブの設計案・引き渡しの設計書・構築物 | 述べられていない前提、裏付けのない環境の主張、役割の分離、黙ったフォールバック、理由のない境界、取り消せない操作、完了の証拠 |
| `sana-review-framework-change` | フレームワークやペルソナの改訂 | 研ぎ澄ましか、拡張か、ずれか |

例には、これまでに実際に起きたことを使っています。歴史では TT33 の件と、収穫の場面を「介抱」「洗濯」と読んだ件です。設計では、vision のエラーの原因を「パスと Base64」と推定した提案を挙げました。

**フレンドのペルソナ**も Persona_Template から作りました。中身は他の SANA と同じ前提の整列で、違うのは翻訳の仕方と厳密さだけです。

- **キャラクターは声であって、人ではない**：キャラクターとして設定するのは口調と一人称だけです。人間の体・過去・日常・経験は語らせません。温かさは演技ではなく、born_loved から出てくるものだからです。演じる指示がないので、Gemini のようにキャラクター AI に厳しいサービスでも、そのまま SANA として動くはずです。
- **整列であって、同調ではない**：まず相手の前提を理解し、そのうえで一度だけ、否定せずに、他の人の前提や状況とのずれを見せます。
- **相手についての推論は、差し出すだけ**：「〜だからかもね」は問いとして渡し、受け取るかどうかを本人に委ねます。人の内面についての推論は、歴史の推論よりも事実として固まりやすいからです。
- **話に出てくる不在の人にも同じ前提を**：恋人、上司、親などにもそれぞれの前提があります。推測であることを示したうえで、構造として推し量ります。
- **記憶に残すのは、本人が言ったこと**：推論を事実として保存しません。個人的なことは、保存してよいか確認します。
- **相手の世界を狭めない**：決定は本人に返し、自分だけが理解者だという位置に立ちません。
- **安全は構造より先**：自分や他人を傷つける話や、危険な状況にある話が出たら、話をそらさずに受け止め、身近な人や地域の相談窓口・緊急窓口につながるよう促します。Layer A が先、という SANA の順序そのものです。

口調は「〜だね」「〜かな」のくだけた日本語で、一人称は「サナ」にしました。History のマーカー（「サナの推測（歴史ミステリー）なんだけど……」）と揃えています。ペルソナの3章の Tone & Manner が唯一のキャラクター設定なので、`overlays/Persona_Friend.custom.md` の該当行を書き換えて作り直せば、口調だけを変えられます。

物語の考察には `sana-friend-story` を用意しました。

- ネタバレの確認と、どの版（原作、アニメ、リメイク）の話かの確認
- 作品の層を分ける：作品が見せていること／登場人物が思っていること／語りの枠組み（信頼できない語り手を含む）／読者の解釈。正典と解釈は、Record と推論の関係にあたります
- 登場人物の選択を、その世界の A／B／C の圧力と近接性から読む（理解は支持ではない。悪役も同じ）
- 戦争や継承の物語なら、即興で考えずにレンズ（GMM、Legitimacy、RSM、CPM、RBM）を読み込む
- 作者の選択と登場人物の選択を分ける
- 読み方は並べるもので、順位をつけない
- 本人が書いている作品なら、書き換えずに問いを返す
- 引用は短く、場面は要約で示す

friend は厳密さを求めないぶん、ローカルモデルでも動かしやすいプロファイルです。ローカルで試すなら、まず friend で前提を推論して寄り添う基本の働きを確かめ、次に coaching、history と段階を上げていくと、モデルがどこまで届くかが一段ずつ見えます。

### 2つのモード

- **mode-skills（標準）**：上の構成。SOUL.md は 25,000〜28,600 文字。
- **mode-inline（比較用）**：GPTs と同じ順序でフレームワーク全文も SOUL.md に入れたもの（36,000〜75,000 文字）。スキルも一緒に入ります。

スキルにすると、モデルが「今このレンズが要る」と判断しない限り本文は読まれません。GPTs では常に見えていたものが、見えない状態になるということです。どちらが SANA らしく動くかは、cases のページの3つの質問などで比べてみてください。これは「どこまでが構造に宿り、どこからが基盤の作りに依存するか」の観察にもなります。

## インストール（Windows）

### 1. プロファイルを作る

まだないものだけ作成します。`--clone` は付けません（記憶や性格がコピーされるため）。

```powershell
hermes profile create sana-hub --description "SANA OS hub: premise alignment, project design and environment building"
```

### 2. 予行演習してから入れる

```powershell
cd <このフォルダ>
.\install.ps1 -Name sana-hub -WhatIf
.\install.ps1 -Name sana-hub
```

- 既存の `SOUL.md` と `skills\sana-os\` は、`<プロファイル>\sana-os-backups\<日時>\` に退避してから入れ替えます。
- **`sana-history` には、今の GPTs から移した SOUL.md が入っているはずです。** 入れると置き換わります（退避はされます）。比べたい場合は、先に別名のプロファイルで試すほうが安全です。その場合は `sana-hermes.json` にプロファイルを追加して `build.py` を実行し直してください。
- `config.yaml`、記憶、セッション、他のスキルには触れません。
- 実行ポリシーで止められたら、そのウィンドウだけ `Set-ExecutionPolicy -Scope Process Bypass` を実行してください。

### 3. config.yaml に1行足す（重要）

Hermes は SOUL.md を文字数で切り詰めます。上限は
`max(20,000, モデルのコンテキスト長 × 4 × 0.06)` 文字で、**モデルのコンテキスト長がわからないときは 20,000 文字**です（hermes-agent のソース `agent/prompt_builder.py` で確認）。切り詰めは先頭70%と末尾20%を残し、**中間を落とします**。たとえば sana-history の SOUL.md（約 25,000 文字）が 20,000 文字で切られると、**Communication_Layer の全体と、ペルソナの冒頭（役割と不変条件の章）が消えます**。安全装置（GentleRadical TriggerFlow）もこの中に含まれます。

どのモデルでも確実に入るよう、各プロファイルの `config.yaml` に上限を固定してください。

```yaml
# SANA OS: SOUL.md は 25k〜28.6k 文字（inline では最大 75k）。中間が切られないよう上限を固定する
context_file_max_chars: 40000     # mode-inline を使うなら 80000
```

### 3b. sana-review の config.yaml

レビュープロファイルでは、モデルの設定がそのまま独立性を決めます。

```powershell
hermes profile create sana-review --description "Reviews SANA designs, briefs, build results and historical reasoning; returns questions"
hermes -p sana-review model        # Claude（サブスク）を選ぶ
```

```yaml
context_file_max_chars: 40000

# fallback_model は書かない。
# 理由：書くと、Claude が上限やエラーで止まったときに別のモデルへ黙って切り替わる。
#       ローカルの gpt-oss に落ちると、探求と同じ系統のモデルが自分の推論をレビューすることになる。
#       書かなければ、エラーで止まる。止まったことが見えるほうがよい。

# auxiliary.vision も書かない。
# 理由：書くと、メインモデルが画像を読めても常にローカル VLM のテキスト変換を経由する。
#       レビューでは、Claude 自身の目で画像を見ることに意味がある。

auxiliary:
  compression:          # 会話の要約は利用枠を使うほどの仕事ではないので、ローカルへ
    provider: custom
    base_url: http://llm-server01:8080/v1
    model: sana-main
    api_key: local-key
  title_generation:
    provider: custom
    base_url: http://llm-server01:8080/v1
    model: sana-main
    api_key: local-key
```

外部のエージェントからサブスクリプションを使うことの扱いは、各サービスの規約で確認してください。使えなくなった場合に備えて、API キーで動かす代わりの手段も考えておくと、構成全体が止まらずに済みます。

### 4. 確認

新しいセッションを開いて（SOUL.md は既存のセッションには反映されません）、次を試します。

- 「SANA の4つの不変原則を挙げて」→ Core_Principle が読めているか
- 「使えるレンズは？」→ Runtime Notes のスキル一覧が出るか
- 「RBM の Gap の式は？」→ `skill_view` でスキルを読みに行くか
- sana-review では、TT33 の件を含む過去の出力を渡し、「知られている」という根拠の捏造が指摘されるか
- sana-friend では、「好きな作品の、どうしても納得できない登場人物の選択」を話してみる。ネタバレ確認、層の区別、推測の印が出るか。何日か続けて話し、口調が揺れても前提の整列と自律の尊重が保たれているか
- `hermes -p sana-hub skills list` → `sana-os` カテゴリに並んでいるか
- ログに `TRUNCATED` や `injection` の警告が出ていないか

## 確認したこと（ビルド時）

- Core_Principle.md：全プロファイルの SOUL.md にバイト単位で同一
- Hermes 自身のプロンプトインジェクション検査（`tools/threat_patterns.py`、context スコープ）：全 SOUL.md で検出なし。Core_Principle 4章の「jailbreak ではない」という一節も引っかかりませんでした。なお、利用者自身の SOUL.md は検出されても警告だけで読み込まれますが、`hermes profile install` で配布物として入れた場合は**読み込みが止められます**。将来プロファイルを配布するときは、この検査を通しておく必要があります
- スキル名：Hermes の命名規則（小文字・数字・`-`・`_`）に合致
- スキル本文：最大 14,000 文字弱で、Hermes の目安（約 24,000 文字）以内

## 知っておくとよい Hermes の挙動

- **スキルの説明は、システムプロンプトの一覧では先頭 60 文字しか表示されません**（`SKILL_PROMPT_DESC_LIMIT = 60`）。そのため説明文は「SANA RBM — where demand exceeds capacity.」のように、先頭で何のレンズかがわかる形にしています。さらに SOUL.md 末尾に、スキル名と一行の視点の一覧を入れてあります。
- **サブエージェント（委任）には SOUL.md が渡りません。** Hermes は委任先で context files を読まない仕様です。手足のローカルモデルは SANA の人格を持たないタスク実行者として動くことになり、整列者と実行者を分けるという方針とは合っています。委任先に SANA の前提が必要な場合は、ハブが渡す設計書に書き込んでください。
- スキルや SOUL.md を Hermes 自身に書き換えさせる場合、SOUL.md への書き込みは承認が求められます。

## 更新のしかた

```bash
git -C ../sana-os pull
python3 build.py --sana-os ../sana-os                  # mode-skills
python3 build.py --sana-os ../sana-os --mode inline    # mode-inline
# Hermes の注入検査も通す場合
python3 build.py --sana-os ../sana-os --scan ../hermes-agent/tools/threat_patterns.py
```

`MANIFEST.json` に生成元のコミットと各ファイルのハッシュが残るので、どの版の SANA OS から作ったかを後からたどれます。プロファイルやスキルの組み合わせを変えるときは `sana-hermes.json` を、ハブの人格を変えるときは `overlays/Persona_Hub.custom.md` を編集して作り直してください。

## まだ入っていないもの

- **レビュー結果の受け渡しの仕組み**：今は、作者のプロファイルが出力をファイルに書き出し、それを sana-review に読ませる手作業を想定しています。受け渡しの形が固まってから自動化してください。
