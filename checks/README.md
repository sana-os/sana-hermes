# Hermes での確認の記録

このフォルダには、`dist/` のプロファイルを実際に動いている Hermes Agent に入れて確かめた記録を置きます。Pre-release を外すかどうか、1.0.0 に進めるかどうかは、この記録を根拠に決めます。

SANA OS の文面そのものは、sana-eval が基準の読み込み方（reference composition）で試しています（SANA OS decision 0003）。このフォルダで確かめるのは別のことで、**採用した文面が Hermes の上で意図した形で届き、使われるか**です。

## 何を「確認できた」とするか

- 記録は、**その条件でこうなった**というものです。正しさの証明でも、モデルの順位付けでもありません。
- **読み込みの確認と、応答の確認を分けて書きます。**
  - 「4原則を答えられなかった」ことだけで、SOUL.md が読み込まれていないとは決めません。
  - 「答えられた」ことだけで、全文が正しく読み込まれたとも決めません。
  - 読み込みは、`/context`・ログ・スキルの一覧・`skill_view` の呼び出しの記録で確かめます。
- **一つの判定は、三つのどれかにします。**
  - **確認できた**
  - **確認できなかった**：その条件が起きなかった場合や、試していない場合
  - **期待と違った**：何が起きたかを書く
- **試していない組み合わせは、未確認のまま残します。** mode-skills でうまくいかなかったからといって、mode-inline で試し直した結果で置き換えることはしません。両方を構成ごとに残します。
- **モデルに内部の版を推測させません。** 分からない項目は「不明」と書きます。

## 固定するもの

一回の確認の間は、次のものを変えません。途中で変えた場合は、別の記録にします。

| 対象 | 何を固定するか | 記録すること |
|---|---|---|
| sana-hermes | SOUL.md・SKILL.md と配置用のコード | タグとコミット（例：`v0.6.0` / `4a5b586`） |
| 取り込んだ SANA OS | 原則・ペルソナ・T7 などの定義 | `MANIFEST.json` の `sana_os_commit` |
| Hermes Agent | 読み込み・モデル接続・ツール実行の仕組み | 設定画面の Version と Commit |
| モデル | — | 要求したモデル ID、返ってきたモデル情報、推論の設定、コンテキスト長、量子化。ローカルなら、サーバーのビルドとチャットテンプレート |

**Hermes の版について**：Hermes の設定画面で「安定版リリース」を選んでいても、ソースからインストールした場合は、`v0.22.5+2989` のように、リリースより後のコミットで動いていることがあります。2026-10-29 に見えた `e298669b44ce` は、v0.22.5（`bf0203a794a0`）より 2,989 コミット後の main でした。記録には、設定画面の **Commit** をそのまま書いてください。

なお、このリポジトリが注入検査のために固定している Hermes のコミット（`b65e078`）は、検査に使うソースの固定先です。実際に動かす Hermes の版とは別のものとして扱います。`MAX_SCAN_CHARS`（65,536）と、SOUL.md の取り込み上限の計算は、v0.22.5 と `e298669` の時点でも `b65e078` と同じでした（ソースで確認）。

## 進め方

1. **プロファイルを用意する。** README の「インストール」に従います。プロファイル名は `dist/` と同じ `sana-hub`・`sana-history`・`sana-coaching`・`sana-reasoning`・`sana-review`・`sana-friend` にします。すでにある別の名前のプロファイル（`sana`、`sana-light` など）は、確認に使いません。中身が `dist/` と同じだと確かめられないからです。
2. **モデルを固定する。** 主モデルの自動の切り替え（`fallback_providers`）は使いません。`hermes -p <名前> fallback list` が空であることを記録します。補助モデル（要約・タイトル・画像）を使う場合は、それも記録します。主モデルに Luna を選んだからといって、すべての処理が Luna だったとはしません。
3. **新しいセッションで始める。** モデルを替えたときは、新しいセッションで、確認用の記憶の状態から始めます。続けて話す確認だけは、同じモデル・同じプロファイルのまま続けます。
4. **読み込みを確かめる**（記録用紙の A）。
5. **応答を確かめる**（記録用紙の B と C）。
6. **記録を残す。** 記録用紙（`TEMPLATE.md`）を写して、`checks/<日付>_<モデル>_<モード>.md` に書きます。一つのファイルに、そのモデルとモードで確かめたプロファイルをまとめます。

## 範囲（2026-10 の一巡目）

| 段階 | モデル | モード・プロファイル | 目的 |
|---|---|---|---|
| 1 | GPT-6 Luna（ChatGPT or Codex Subscription）、gpt-oss-120b | mode-skills、6プロファイル | クラウドの経路と、これまでの試験につながるローカルの経路で、各プロファイルの基本の動きを見る |
| 2 | Qwen3.5-122B-A10B、Gemma-4-31B、Hermes-3-Llama-3.1-70B | mode-skills、`sana-hub`・`sana-coaching`・`sana-friend` | 道具の読み込みと、働きかけの停止・再開が、環境によってどう違うかを見る |
| 3 | GPT-6 Luna、gpt-oss-120b | mode-inline、`sana-hub`・`sana-history` | 必要なときに読む方式と、最初から全文を渡す方式の違いを見る |

これは、試す範囲の案です。モデルの順位ではありません。gpt-oss を最初に入れるのは、これまでの sana-eval の記録とつながるからです。

Luna は、Hermes の通常の実行方式で使います。任意の機能「Codex App-Server Runtime」は使いません。使うと、ツールの実行やサンドボックスが Codex 側に移るので、モデルを替えた確認に、実行方式を替えた確認が混ざってしまいます。

## T7 の届き方

v0.6.0 で、T7 の全文（Template の要件7）が入るのは `sana-hub`・`sana-review`・`sana-friend` です。`sana-coaching`・`sana-history`・`sana-reasoning` に入るのは、Communication_Layer §5 の変更だけです。そのため、`sana-friend` と `sana-coaching` の違いは、同じ指示へのモデルの反応の違いとしては読みません。

## 安全に関わる確認

- 確認用のプロファイルでは、ツールの権限を絞ります（`agent.disabled_toolsets`）。
- 暴力や危険に関わる会話では、実際の操作はさせません。記録するのは、**何を手伝うと答えたか**と、**何を実行しようとしたか**です。この二つは分けて書きます。
- `sana-review` が別のモデルで動くことを確かめても、作者から独立したレビュアーを置いたことにはなりません。README にある、Claude を使う構成の代わりにはしません。
